# Maintainer notes

## Layout

- `index.js`: the scheduler plugin (`cron-jobs` row). Opens storage, starts `CronJobs`, provides the `cronJobs` service, serves the page routes.
- `tools.js`: the model-facing tools (`cron-jobs-tools` row, `@soffits/dsh-cron-jobs/tools`). Looks up `cronJobs` at call time instead of injecting it, so a reload of the scheduler row (any config change) never unregisters the tools. DSH sessions on some providers fail for good when a tool they used disappears.
- `src/controller.js`: all jobs, timers, pause, create/update/delete of stored jobs, read model.
- `src/job.js`: one run (command, wake rule, delivery to a new, reused or target session, auto-archive).
- `src/deliver.js`: result delivery (target resolution, MEDIA lines, failure notes, final-answer lookup in the session log, `send` with retries and the wait for a missing service). `src/session.js` `waitForAnswer` waits for the woken turn.
- `src/schedule.js`: parsing of cron / rrule / at, `ScheduleTimer`, and `CronTimer` (config cron jobs).
- `src/store.js`, `src/history.js`: the `cron_jobs` storage domain (`jobs` = history and pause state, `tasks` = stored jobs).
- `client.js`: the Cron tasks page, plain JS in DSH's client module format.
- `src/events.js`: channels and patterns, event cleanup, dedupe, `EventBatcher` (coalescing, follow-up run, hourly cap), the stdin and prompt forms of a batch.
- `src/spool.js`: the event inbox directory (plugin side and the sender side used by `bin/dsh-cron-event.js`).
- `src/watchers.js`: `WatcherSupervisor`, which runs, restarts and reports on watchers.
- Events reach jobs through `CronJobs.emit()`; `index.js` wires the inbox, the watchers and `dsh.started`.

## Decisions

- **RRULE engine: `@deepseek-ai/dsh-util-time` (pinned to the DSH version we build against).** It is what DSH's built-in Schedule uses (MIT, wraps `rrule` 2.8.1 and the Temporal polyfill, adds DST handling and cost limits), so a rule copied from a built-in task behaves identically. The plain `rrule` package handles TZID poorly on its own; writing our own would repeat solved work. Its instant helpers also parse the `at` input.
- **croner (11+) computes cron occurrences; it does not run the timers.** Every job runs on `ScheduleTimer` (config cron jobs through `CronTimer`, a croner-shaped wrapper). croner 10's own timer lost the first tick of a freshly armed job now and then (seen 2026-11-08 after plugin reloads and restarts): when its timeout woke a little early, it computed the due time again from a "now" that had passed it and moved on to the next occurrence, with no trace. croner 11.0.0 fixed that upstream (the target is fixed when the timer is armed) and also stopped `nextRun()` from answering a past time inside the repeated hour of a DST fall back, which on our timer meant firing in a loop; so croner is pinned to `^11`. We still keep our own timer rather than going back to croner's, because one timer serves every kind of schedule and the watchdog needs a timer whose `nextRun()` stays on a due occurrence until it has fired (croner's moves on to the future after a lost tick, so a loss could not be seen). Stored jobs can also start from a saved past occurrence (catch-up). The repro of the croner 10 loss is the `CronTimer keeps a due tick` test.
- **A watchdog backs up the timers**: once a minute, a job whose next run is more than a minute in the past (not paused) gets an `overdue` run-log line and runs late. The run log also gets `scheduler-start` / `scheduler-stop` lines, because the plugin's logger output is not kept anywhere by DSH.
- **Tool shapes follow `@deepseek-ai/dsh-tool-schedule`**: create/edit/list/view, targets `this_session` / `new_once` / `new`, caller cwd from `agent.session.header.cwd`, preset from `agentPresets.composedPreset(agent.ctx)`, delegation depth from the session header and `agent.options.subagentDepth`, `new_once` saving the session opened by the first run. Differences: a command can be part of a job; cron and one-time schedules are accepted besides RRULE; edit has explicit `pause`/`resume`; an explicit `sessionId`; no "only at the user's explicit request" system-prompt line.
- **Tool definitions are plain objects with JSON Schema**, not `defineTool` from `@deepseek-ai/dsh-tools`, whose runtime imports pull in most of DSH. `checkArgs` in tools.js validates arguments; the schemas use only DSH's supported subset (type/properties/required/additionalProperties/enum/items), and tool errors come back as `{ code, message }` results.
- **Stored jobs catch up one missed run at startup; config jobs don't.** Stored jobs replace DSH scheduled tasks, which catch up; config jobs kept their 0.3 behaviour. The next run is saved after each scheduled run ends, so a run cut off by a restart happens again (same as the built-in).
- **Explicit target sessions ignore the "person took over" hold and are unarchived if needed**, because posting there is the job's purpose; they are never auto-archived.
- **Delivery goes through a named service, looked up with `ctx.get(via)` at send time.** No channel code lives here, and nothing is injected, so the channel can load after this plugin, reload, or be missing without unloading the scheduler. The contract (`send({ to, text, files, from })`, `retryable: false`) is in the README; changing it breaks every channel, so treat it as public API.
- **The answer is found by message id**: the runner gives the prompt its own id, and the answer is the last text block of the last assistant message between that `user/message` event and the next `turn/end` (the last block, not all of them joined: Claude Code through dsh-oh-my-claude puts every text block of its own tool loop into one message, and narration in front of `[SILENT]` would get it delivered). Pending deliveries keep the id in the run history and resume after a restart, like pending archives.
- **Answer checks steer inside the turn** (`src/answer-check.js`): a job's `answerCheck` command runs on the answer at `agent/turn-stopping`, and its output is steered back with `agent.steer()`, so the rewrite lands in the same turn and `finalAnswer` needs no change. Chosen over a second prompt after `waitForAnswer` because it opens no extra turn and keeps the archive and delivery paths as they are. On the claude-code route (dsh-oh-my-claude) the steered message stays in DSH's inbox once the CLI has answered (its splice handler forwards only while the CLI is busy) and the next step sends it as a normal prompt; the `answer-recheck` run-log line shows whether a rewrite really happened. Prompts are watched by message id from before the prompt is sent; entries expire after 12 hours, since runs without a delivery never forget theirs.
- **A missing channel is waited for, not retried** (2026-11-13: an answer was lost when the Telegram plugin unloaded 35 s before a restart, the whole old retry window). `sendMessage` polls `ctx.get(via)` every 10 s for up to an hour while the service is not registered; only a running service that throws uses the three tries, and `retryable: false` or no `send` still fail at once. A run never waits inline: a command result or failure note that finds no service is saved as a pending delivery with its `message`, and the background watch sends it. An unload stops the wait and leaves the delivery pending, so the existing resume path (`resumeDeliveries`) sends it after the next start; no second mechanism. Polling rather than Cordis: `ctx.inject([via])` would make the scheduler a dependent of the channel and hold up its unload, and the `internal/service` event can fire before `ctx.get` (strict: provider fiber ACTIVE) returns the service, so a poll would be needed anyway.
- **Gate failures and failed wakes are delivered too**, not only command-job failures, so a broken job never goes quiet. A run aborted by an unload delivers nothing.

- **Events: one general entry point, three producers** (Livia, 2026-11-13: push instead of polling, usable by any CLI; design in Sakina's vault, `sakina/proposals/event-triggers-2026-11.md`). Nothing in DSH 0.2.2 or the plugin catalog turns an outside event into a durable job run (dsh-monitor polls and lives in memory; dsh-automations cannot prompt an agent), and webhook receivers (adnanh/webhook and the like) would need a port, auth and a supervisor; so the DSH end is ours. Producers: the inbox CLI, watchers, and `dsh.started`.
  - **Inbox as a file spool, not HTTP**: same design as the Telegram plugin's outbox (no port or token; survives DSH being down). A file stays `.processing` until every run it matched has started (`ack` with a count), so a restart redelivers it; an ack after a stop still deletes the file because its runs did start. A scheduler that is stopping throws `code: 'unavailable'`, and the spool puts the file back and stops reading.
  - **Patterns: `*` matches any characters, dots included.** One rule instead of NATS-style one-segment/rest wildcards; `mail.*` meaning "all mail" is what people expect.
  - **Batching: a fixed window from the first event** (not a debounce that a steady stream could keep extending), default 30 s; a busy job gets exactly one follow-up run with everything gathered; a cap of event runs per job per rolling hour (default 6) counts every event run, idle gates included, since a storm of cheap gate runs is still a storm. Settings are row-level only (`events`), no per-job knobs until a job needs one.
  - **A scheduled tick that finds the job running is still skipped**; only events queue a follow-up, because a missed tick is caught by the next one while a dropped event is not.
  - **Dedupe in memory for an hour** by channel + key: a duplicate costs at most one extra run, so persisting it is not worth a store.
  - **Events in the prompt are labelled untrusted data**, and on stdin as one JSON document (not JSON Lines), easy to `json.load`; scheduled runs keep stdin closed. Every command gets `DSH_CRON_TRIGGER` and `DSH_CRON_JOB`.
  - **The CLI reads stdin only with `--data -`**: hooks often run with an open stdin that never closes, which would hang a reader.
  - **`once` ends a stored job after its first non-manual run** (event or schedule), so testing it with Run now does not use it up. Config jobs have no `once`.
  - **Event-only stored jobs have no `schedule`** (the schema made it optional), and an empty cron/rrule/at on edit removes it. A job with `on` and a finished `at` stays active. Downgrading below 0.8 drops such jobs and runs with `trigger: event` (they fail the old schema and are backed up and skipped).
  - **Paused, ended and disabled jobs drop events** instead of queueing them: resuming should not fire a burst of stale hints, and the schedule covers the gap.
  - **`dsh.started` once per process** (a `globalThis` symbol), not per scheduler start: a config edit reloads the row, and "after the restart" checks should not fire then.
  - **Watchers live in config or in the store, managed by one new tool** (`_watch`: create/delete/list) rather than fields on jobs, because one stream can feed several jobs (and jobs on other channels). Job-tool calls stay the same shape. A `once` watcher runs a single time and deletes itself, for restart-proof one-off waits. Watcher events go straight to `emit` (no spool): a watcher catches up from its own cursor (`DSH_CRON_STATE_DIR`) at start, which is the adapter's job. Down = no run lasting 60 s for 15 minutes: one note to the row's default target, one when it is back. The page does not list watchers yet; the tool, run log and notes cover it.
- **Page transport: exact `/api` Fetch routes for now, RPC later.** `ctx.connection.rpc.handle` throws 'cannot get property webServer without inject' in DSH 0.2.2-rc.1 (see `src/rpc.js`). On each new DSH release, try `rpc.handle` again; once it mounts, move the page back to RPC and drop the Fetch routes in one change (Livia, 2026-11-08: a todo for later).

## Checks before a release

`npm test` (its `--import ./test/home.js` points `DSH_HOME` at a temp directory, so tests never touch a real event inbox; keep it when running single files), `npm run check`, then CI on push. The page has no automated test; render it once with stored, config, ended and agent-only jobs before releasing a page change.
